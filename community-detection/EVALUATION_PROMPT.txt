You are helping me analyse results for a university data mining group
report comparing community detection algorithms. My part is:
[MY ALGORITHM]. I've attached our result files and figures.

## Project context (use this, don't assume anything else)

- Methods compared: Louvain, Leiden, Infomap, Bayesian SBM (graph-tool,
  degree-corrected), Spectral clustering (normalised Laplacian +
  K-means). Spectral was GIVEN THE TRUE NUMBER OF COMMUNITIES K by the
  harness; the others were not. Always mention this when comparing
  Spectral's accuracy.
- Experiment 1: LFR synthetic graphs with known communities.
  - Mixing mu = share of each node's links that go to other
    communities. Higher = harder. Tested mu = 0.2, 0.4, 0.6 at
    n = 1,000 nodes.
  - Each mu has 2 different random graphs (graph seeds s1, s2).
  - Scale test: n = 1,000 / 10,000 / 50,000 at mu = 0.4.
- Experiment 2: email-Eu-core, a real email network where the "true"
  communities are 42 departments. data/email/summary.csv gives its own
  mu, which places it on the LFR difficulty curve.
- Every graph was run with 5 algorithm seeds (0 to 4). summary_table.csv
  is already averaged over seeds (NMI = mean, NMI_sd = spread).
  Fig 1 averages over both graph seeds and algorithm seeds.
- Metrics: NMI and ARI (1 = matches the truth perfectly, 0 = no
  better than random); modularity of the found partition vs of the true
  partition; n_found vs n_true communities; frac_disconnected = share of
  found communities that are internally split; runtime_s; stability =
  NMI between runs with different seeds (1 = same answer every time).
- Runs over 15 minutes were stopped and recorded as "timeout". A timeout
  is a result, not a missing value.

## Rules

1. Use ONLY numbers that appear in the attached files. Quote them as
   mean +/- sd with 2 decimals (e.g. "NMI = 0.93 +/- 0.02"). If
   something I ask for isn't in the data, write "NOT IN DATA". Never
   estimate or invent a number.
2. After every number, say which file or figure it came from, in
   brackets, e.g. (summary_table.csv, mix_mu0.6_s1) or (Fig 1).
3. Every finding follows CLAIM -> EVIDENCE -> MECHANISM -> SO WHAT:
   - CLAIM: one sentence
   - EVIDENCE: the numbers
   - MECHANISM: WHY, using how [MY ALGORITHM] actually works
   - SO WHAT: what a practitioner should take away
4. Don't just restate a figure ("NMI decreases as mu increases").
   Every finding needs a reason.
5. Don't invent citations. The only references we use are: Blondel et
   al. 2008 (Louvain), Traag et al. 2019 (Leiden), Rosvall & Bergstrom
   2008 (Infomap), Peixoto 2014 (Bayesian SBM), Ng, Jordan & Weiss 2002
   (Spectral), Lancichinetti et al. 2008 (LFR).
6. Plain English, short sentences. No filler.

## What I want, in exactly this order and with these headings

### B. Experiment 1 (LFR): the facts
A small table for [MY ALGORITHM] with one row per graph: NMI, ARI,

- how it ranks against the other methods at mu = 0.6 and at 50k

### C. Experiment 2 (email): the facts

### E. Parameter sensitivity

### F. Ablation
